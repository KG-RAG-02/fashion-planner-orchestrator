# 0002 · 직접 만든 순차 워크플로와 SQLite 체크포인트

- 상태: 채택
- 범위: orchestrator

## 맥락

한 실행은 여섯 단계를 정해진 순서로 지나가고, 일부 단계는 유료 모델을 부른다. 필요한 것은 복잡한 분기가 아니라
다음 세 가지였다.

- 단계마다 서비스 응답 원문을 그대로 보관한다.
- 같은 요청을 다시 받으면 서비스를 다시 부르지 않는다.
- 결과를 모르는 호출(프로세스가 그 사이에 죽은 경우)을 자동으로 반복하지 않는다.

## 결정

- 단계 실행 루프를 직접 만든다(`workflow.py`). 단계 순서는 `STAGES` 하나로 고정한다.
- 상태는 단일 호스트 SQLite(`checkpoints.sqlite3`)에 둔다. 호출 전 `started`, 결과 `done`을 기록하고, `started`만 있는
  단계는 `409 STAGE_OUTCOME_UNKNOWN`으로 닫힌 쪽으로 실패한다.
- 자동 재시도는 하지 않는다. 6단계 기획서만 재시도 키로 따로 다시 그릴 수 있다.

## 결과

- 실행 하나의 모든 호출과 원문이 실행 기록에 남고, 같은 `request_id`는 저장된 결과로 답한다.
- 유료 호출이 결과를 모른 채 두 번 나가지 않는다.
- 여러 호스트가 함께 쓰는 고가용성 구성은 지원하지 않는다.

## 검토한 대안

| 대안 | 택하지 않은 이유 |
|---|---|
| LangGraph | 복잡한 분기·사람 개입 중단에 강하지만, 이 흐름은 고정 순서다. 외부 호출의 멱등성은 어차피 직접 다뤄야 한다 |
| Temporal 같은 워크플로 엔진 | 장기 실행·분산 작업용이다. 서버 운영 부담이 이 규모에 비해 크다 |
| 서버 DB(PostgreSQL 등) | 여러 호스트가 함께 쓸 때 필요하다. 지금은 단일 호스트의 작은 트랜잭션이라 SQLite로 충분하다 |
