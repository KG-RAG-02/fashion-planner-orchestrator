# 0006 · 단일 호스트 Docker Compose 프로필

- 상태: 채택
- 범위: 배포

## 맥락

다섯 서비스와 Neo4j, 캐시, 볼륨, 네트워크를 한 대에서 재현해야 했다. 처음 써 보는 사람은 계정·데이터·비용 없이 전체
흐름을 돌려 볼 수 있어야 하고, 실제 데이터와 유료 모델은 명시적으로 켰을 때만 써야 했다.

## 결정

- `deploy/compose.yaml`을 기본으로 프로필 세 개를 더한다: stub(합성 데이터, 오프라인), rehearsal(직접 준비한 Aura·R2, 유료 호출
  없음), live(rehearsal + OpenAI). 실행은 `deploy/bin/fashion-planner`로 한다.
- 모든 앱 컨테이너는 읽기 전용 루트, uid 10001, 선언한 볼륨·tmpfs만 쓰기 가능하다. orchestrator 포트만 127.0.0.1에 공개하고,
  서비스끼리는 내부 `backend` 네트워크와 공용 bearer 토큰으로 통신한다.
- live는 가드 파일로 한 번만 실행되고, 유료 키는 `compose.paid.yaml` 한 파일만 참조한다. research의 H&M 자료 사용과 외부 LLM
  전송은 env 파일에서 1로 켜야 한다.

## 결과

- stub은 Docker와 레포 다섯 개만 있으면 돈다(이미지 빌드와 Neo4j 이미지 내려받기에만 네트워크가 필요하다).
- 여러 호스트, 자동 확장, 고가용성은 지원하지 않는다.
- 프로젝트·볼륨 이름이 프로필별로 달라 실행 기록이 섞이지 않는다.

## 검토한 대안

| 대안 | 택하지 않은 이유 |
|---|---|
| Kubernetes, 관리형 작업 실행기 | 여러 호스트·자동 확장 요구가 생겼을 때 다시 비교한다. 지금은 운영 부담이 크다 |
| 레포마다 따로 실행하는 스크립트 | 개발용으로는 남겨 두었다(`scripts/local_servers.py`, `deploy/service-manifest.json`). 컨테이너 격리와 볼륨 규칙을 재현하지 못한다 |
